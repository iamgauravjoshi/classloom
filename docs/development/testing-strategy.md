# Testing strategy

Run lint, strict typecheck, unit tests, and builds on every change. Domain rules get focused unit tests. Database adapters and API behavior get integration tests against PostgreSQL. Run `pnpm exec dotenv -e .env -- pnpm test` locally to load database credentials and include PostgreSQL integration tests; plain `pnpm test` does not load `.env`, so those tests skip. Critical school workflows get end-to-end tests as their modules arrive. Tenant isolation is a mandatory integration gate for every tenant-owned module starting in Phase 1. Tenant integration tests must connect through the non-owner `classloom_runtime` role; database setup and migrations use `DATABASE_MIGRATION_URL`.

Phase 1 database integration coverage verifies that the configured runtime role is a non-owner, non-superuser without `BYPASSRLS`; tenant A can insert and update its own school/campus rows; cannot read, update, or delete tenant B rows by direct UUID; cannot insert or update rows with a different tenant ID on either table; receives no tenant-owned rows and cannot write to either table without context; cannot point a campus at another tenant's school; and does not leak transaction-local context across a reused connection. Provisioning tests verify slug conflicts, school-code uniqueness within one tenant, atomic rollback, and CLI argument validation.

Phase 0 tests API health and error envelopes, configuration validation, database connectivity and migration repeatability, and navigation visibility. Browser smoke checks cover desktop/mobile shell, theme, keyboard navigation, loading, and empty states. Tests use deterministic fixtures; generated demo data is never a security test substitute.

Use Faker.js (`@faker-js/faker`) when realistic generated fixture or demo values improve coverage. Seed it for repeatable tests, and keep security and tenant-isolation tests explicit about identities, tenant IDs, and expected access; random-looking data is not evidence of isolation. Faker data must never contain or imitate real student or staff records.

Phase 11 verifies exact hundredths and zero scores, roster snapshots, incomplete submissions, draft/submit/return/lock/complete transitions, stale concurrent saves, rollback with audit, reviewed corrections, self-approval denial, exact teacher section/subject restrictions, school and tenant isolation, scoped foreign keys, and runtime audit immutability. Authenticated API checks include CSRF and strict inputs. Frontend checks preserve edits on failures, pause repeated writes after failed refreshes, use the shadcn calendar without dismissing the containing form, and hide self-review controls.

Phase 6 tests cover student and guardian normalization, code collisions, relationship responsibilities, account links, school-scoped visibility, enrollment state transitions and concurrency, CSV parsing, mapping, preview, checksum and idempotency, and atomic admission/import transactions. The database integration suite verifies forced RLS through the restricted runtime role, absent tenant context, cross-tenant references, and school scope. API E2E tests exercise permissions, validation messages, cross-school guardian visibility, rollback, transfer, and import retry. Web tests cover directory loading and filters, admission validation, profile tabs, and CSV file limits, mapping, row errors, and retry key reuse. The development seeder uses seeded Faker data for a local smoke run; it is not invoked by application startup or migrations and is not a substitute for security tests.
