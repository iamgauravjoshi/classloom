# Staff and teacher profiles (Phase 5)

Run `pnpm db:migrate` after pulling Phase 5. The new migration creates staff, affiliation, and teacher tables with forced tenant RLS, grants the runtime database role access, and adds `staff.read` and `staff.manage` to the permission catalog and built-in role templates. If the local runtime role is missing, follow [local setup](local-setup.md) before migrating.

Sign in with an active tenant administrator or school administrator account, then open **Teachers & Staff** at `/staff`. Choose a school, search by name or code, and filter by role or status. Add a profile with a tenant-unique staff code and school designation. Mark a teacher affiliation when the person teaches at that school; optional qualification and specialization stay on the shared teacher record. A staff profile has no login credentials until an existing active account is linked. To create that account, use the trusted invitation workflow in [authentication development](authentication.md); there is no public account or invitation endpoint.

Open a profile to edit its school affiliation, shared details, teacher details, or account link. A manager can change designation, start date, staff/teacher role, or active status at their school. Marking an affiliation as teacher creates an empty teacher-details record if needed; qualification and specialization remain shared fields. Shared fields and the account link require `staff.manage` at every school affiliated with the person. Adding another affiliation requires read access to the source profile and manage access to the target school. The account must have an active membership and account status, plus a tenant or school role grant at every active affiliation before linking. A campus-only grant does not qualify for a school-wide teacher assignment. One membership can belong to only one staff profile. Assignments block unlinking or replacing the membership so historical teacher names are not reassigned. Inactivation keeps records and assignment history.

The directory API is under `/api/v1/people`: `GET /schools` lists readable schools; `GET` and `POST /schools/:schoolId/staff` list and create profiles; `GET` and `PATCH /schools/:schoolId/staff/:staffId` read and edit; `POST .../affiliations` adds a school; `PUT .../teacher` saves teacher details; `PUT` and `DELETE .../account` manage the link; `GET /schools/:schoolId/eligible-accounts` lists account choices for managers. List filters are `q`, `status`, `kind`, `cursor`, and `limit` (1–100). Mutations require the existing browser origin and `X-ClassLoom-Request: 1` marker. Tenant identity always comes from the authenticated server session. The same-origin web proxy forwards only these routes and methods.

In Academic Setup, select a section, subject, and teacher. Only active teacher affiliations linked to active accounts and memberships with school grants appear. A profile with no link is not assignable. Historical assignments to accounts without a current profile or grant still display their account label. The API remains the permission boundary regardless of what the page shows.

For focused checks with local PostgreSQL, run `pnpm --filter @classloom/db exec dotenv -e ../../.env -- vitest run staff.integration.spec.ts` and `pnpm --filter @classloom/api exec dotenv -e ../../.env -- pnpm run test:e2e -- people.e2e-spec.ts academics.e2e-spec.ts`. The complete checks are `pnpm lint`, `pnpm typecheck`, `pnpm exec dotenv -e .env -- pnpm test`, `pnpm exec dotenv -e .env -- pnpm --filter @classloom/api test:e2e`, and `pnpm build`.
