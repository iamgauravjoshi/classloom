# Multi-tenancy

ClassLoom uses one PostgreSQL database with a `tenants` control-plane table and tenant-owned `schools` and `campuses`. Each tenant can own multiple schools; each school can own multiple campuses. Every tenant-owned table has a required `tenant_id`. Composite references include the tenant ID so a campus cannot point to a school owned by another tenant.

Every tenant-scoped operation runs inside `withTenantContext(db, tenantId, work)`. The helper validates the UUID, opens a transaction, sets `app.tenant_id` with transaction-local `set_config`, and passes the transaction handle to `work`. Tenant-owned queries, background jobs, exports, and scripts use this helper or an equivalent explicit transaction context. Transaction-local state is cleared when the transaction ends, including when the connection returns to the pool.

Schools and campuses use forced PostgreSQL row-level security. Policies apply the tenant context to reads and writes (`USING` and `WITH CHECK`); a missing context returns no rows and rejects writes. The API runtime connection (`DATABASE_URL`) must be a non-owner, non-superuser role without `BYPASSRLS`. Schema migrations use `DATABASE_MIGRATION_URL`; tenant and school provisioning uses `DATABASE_PROVISIONER_URL`; first-administrator role bootstrap uses the restricted runtime URL and an active tenant membership. Keep privileged URLs server-side. The `tenants` table is control-plane data and is not granted to the tenant-scoped runtime role.

Tenant selection never comes from an unauthenticated request parameter or header. Phase 1 provides the database boundary and a service-only provisioning command, with no public tenant-selection or provisioning endpoint. Phase 2 authentication resolves a user's authorized membership from the server-side session and passes that tenant ID to tenant-scoped services; authorization remains an independent API check. Invitation token lookup is limited by PostgreSQL policy to the supplied high-entropy token hash. The runtime role has a narrow invitation `UPDATE` policy for locking and consuming the row only when the transaction supplies that same token hash; all other invitation writes require tenant context.

To create the first tenant and school in a local environment, run `pnpm db:provision-tenant -- --name "Demo School Group" --slug demo-school-group --school-name "Demo School" --school-code DEMO --timezone Asia/Kolkata --currency INR`. The command requires `DATABASE_PROVISIONER_URL`; unique-constraint conflicts return a provisioning conflict, and tenant plus school creation is atomic.

Every future tenant-owned module must add a non-null `tenant_id`, tenant-safe composite foreign keys, tenant-scoped repositories, and an RLS policy. Isolation tests must cover two tenants, direct-ID access, mismatched writes, absent context, and pooled-connection reuse. An ADR is required for any exception.

Phase 4 academic tables follow this pattern. Sessions reference a school; classes and subjects reference a session; sections reference a class; teacher assignments reference a section, subject, and tenant membership. Composite keys include tenant, school, and session IDs so an assignment cannot combine records from different schools or sessions. The API resolves the tenant from the active server session and verifies `school.read` or `school.manage` for the requested school before accessing these tables.


Authorization roles, role-permission mappings, and membership assignments are tenant-owned tables with forced RLS. Permission catalog reads use the global application-owned catalog; runtime writes to role data run only inside `withTenantContext`. Assignments have same-tenant composite references to memberships, roles, schools, and campuses. Tenant, school, and campus grants follow the scope hierarchy documented in [identity and access](identity-and-access.md); unsupported academic and relationship scopes fail closed.
