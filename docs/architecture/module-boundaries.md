# Module boundaries

The NestJS API has a small common foundation for configuration, request context, error handling, logging, and health. Domain modules will be added in order: tenancy/schools/campuses, identity, authorization, academics, people/enrollment, admissions, timetable, attendance, fees/payments, examinations/results, communication/reporting, then rollover.

Each domain module owns its API, application services, domain rules, persistence adapters, and tests. Modules exchange explicit interfaces or domain events for cross-module effects; database tables are not used as implicit public APIs. The SaaS control plane owns provisioning and entitlements. The school application owns operational student data. Platform administrators do not receive automatic access to that data.

The academics module owns academic session, class, section, subject, and teacher assignment records. Assignments continue to reference tenant membership IDs. For new assignments, Academics calls `PeopleService.canAssignTeacher` within the tenant transaction; it does not read People tables directly. People checks for a linked active teacher affiliation, teacher profile, active account and membership, and a school grant. Older assignments remain readable even if the account has no profile or is disabled. Session activation is serialized on the school row, archives the previous active session, and requires a class, section, and subject.

The People module owns tenant-wide staff identity, school affiliations, teacher details, account-link rules, and staff APIs. It enforces school-scoped `staff.read` and `staff.manage`. Shared profile and account changes need manage permission at every affiliated school. Creating a staff profile never creates an identity account or invitation.

Phase 6 extends People with tenant-wide student and guardian identity, relationships, and optional active-membership links. People owns normalization, code uniqueness, relationship responsibilities, and shared-identity edits. Enrollment owns school admission periods, academic placement history, transfers, withdrawals, completion, and CSV import orchestration. Academics resolves session, class, and section placement through an explicit service contract. Enrollment calls People and Academics application services inside one tenant transaction for manual admission and CSV commit; it does not use their tables as integration APIs. Student lists use an explicit Enrollment query contract for school, session, class, and section visibility. A school-scoped guardian profile returns only student links visible at that school.

Phase 7 adds the Admissions module, which owns school-scoped enquiries, applications, workflow state, and immutable case events. Admissions calls People and Enrollment application contracts during final conversion; it does not write their tables directly. A conversion requires an accepted case and `admissions.convert`, and creates or links People profiles, guardian relationships, the school admission, and the requested initial academic placement in one tenant transaction. A failed People or Enrollment operation rolls back conversion and leaves the case accepted for correction and retry. The separate Admissions permission keeps admissions staff from needing broad student, guardian, or enrollment management grants.

Phase 8 adds the Timetable module, which owns weekly schedules, slots, draft/published state, overlap checks, and timetable audit events. It validates school-session, section, subject, and teacher-assignment references through Academics and People application contracts rather than reading their tables as an integration API. Timetable writes run in the authenticated tenant context, serialize on the parent timetable row, and check section, eligible teacher, and normalized room overlaps. Read-only members see published schedules; editing a published schedule returns it to draft until a manager republishes it. Development seeding is a separate explicit command, uses reserved `DEMO-TT-*` keys, and writes no identity records.

Phase 9 adds the Attendance module, which owns daily registers, per-enrollment attendance states, and immutable correction events. It obtains the roster from Enrollment, sections and sessions from Academics, and linked teacher eligibility from People through explicit contracts in the authenticated tenant transaction. `attendance.read` and `attendance.record` are school-scoped. A teacher profile linked to the active membership can read and record only assigned sections; all other sections require an applicable school grant. Saves validate the exact active roster and serialize on the register so concurrent enrollment changes cannot produce a partial or stale register. Attendance data is tenant-isolated by forced RLS.

Phase 10 adds Finance, which owns fee heads, class/session plans, student plan assignments, charge snapshots, immutable receivables entries, and offline payment receipts. It asks Academics to validate plan classes and Enrollment to validate and lock a student's school enrollment and placement; Finance never queries those modules' tables directly. `finance.read`, `finance.manage`, `payments.record`, and `payments.adjust` are checked at school scope by the API. Account writes serialize on the Enrollment lock, and plan edits/issuance serialize through a transaction advisory lock. Balances derive from append-only minor-unit entries. All Finance rows carry tenant and school keys, forced RLS, and composite references that prevent a ledger entry from crossing student accounts.

Phase 11 adds Examinations, which owns exams, section/subject assessments, roster snapshots, marks, correction requests, and immutable events. Academics provides reference validation and exact teacher assignment options; People provides linked teacher eligibility; Enrollment supplies the date-effective roster when an exam opens. Those integrations use application contracts inside the tenant transaction. Marks writes lock the exam before its assessment and require expected versions. Sheet reads use the same lock order to keep the version and values consistent. Locked changes need a reason and another account's approval. Phase 12 will consume reviewed marks through an Examinations contract.

Phase 12 adds Results as a separate module owning immutable grading policy revisions, report editions/snapshots, staff remarks, and result events. It consumes reviewed marks through Examinations (which locks its own parent exam), historical roster identities through Enrollment, school/academic labels through Academics, and current student/guardian report relationships through People. Results persistence never reads the other domains' tables directly. Result generation and workflow updates serialize exam-first, then edition, with optimistic versions and atomic events. Approved publication replaces the prior current edition without changing its snapshot; withdrawal ends family access while preserving history. See ADR-0010 and the Results development guide.
